下面的函数把 8 字节缓冲区"清空"，但循环边界写错了：

```c
void f(void) {
    char buf[8];
    for (int i = 0; i <= 8; i++)   /* 应该是 i < 8 */
        buf[i] = 0;
}
```

未开启栈保护时，汇编是（`buf` 位于 `%rbp-8`）：

```
f:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp
    leaq    -8(%rbp), %rax      # buf
    xorl    %ecx, %ecx
.L2:
    movb    $0, (%rax,%rcx)     # buf[i] = 0
    addq    $1, %rcx
    cmpq    $8, %rcx
    jle     .L2                 # i <= 8 时继续
    leave
    ret
```

(1) `buf` 的地址是 `%rbp-8`，那么 `i = 8` 时写到了哪个位置？被改成 0 的是哪一字节？

(2) 设 `0(%rbp)` 处保存的旧 `%rbp` 为 `0x00007fffffffe4a0`。函数执行 `leave` 之后 `%rbp` 变成多少？帧指针移动了多少字节？

(3) 返回调用者后，调用者继续用自己的 `%rbp` 访问局部变量和保存的返回地址，会发生什么？为什么这种"帧指针偏移"可能导致控制流被劫持？

(4) 如果给函数开启 `-fstack-protector`（编译器把 canary 放在 `-8(%rbp)`、`buf` 放到 `-16(%rbp)`），`i = 8` 写的就是 canary 的最低字节——为什么 canary 检查发现不了这次越界？

(5) 从代码、编译选项、检查工具三个角度，各给出一种能防住/发现这个 bug 的办法。

## 提示

栈向低地址增长，`buf[i]` 的地址是 `buf + i`；`buf` 结束于 `%rbp-1`，所以 `i = 8` 正好落在 `%rbp` 指向的字节上——那是**保存的旧 `%rbp` 的最低字节**（小端存储时，最低字节在最低地址）。canary 的最低位是编译器特意清零的，所以写入 0 不会改变它。

## 解析

**(1)** `buf` 占 `%rbp-8` 到 `%rbp-1`（8 字节）。`i = 8` 时地址是

\[
\%rbp-8+8=\%rbp,
\]

也就是 `0(%rbp)` 这一字节——保存的旧 `%rbp` 在内存中的**最低字节**（x86-64 小端，低地址存低字节），被写成 `0x00`。

**为什么想到**：先算出缓冲区覆盖的地址区间，再算 `i=8` 的偏移；`%rbp` 处正是「保存的旧帧指针」的第一个字节，而不是返回地址（返回地址在 `8(%rbp)`）。

**(2)** 旧 `%rbp` 是 `0x00007fffffffe4a0`，最低字节是 `0xa0`；把它改成 `0x00` 后：

\[
\begin{aligned}
\text{原值} &= \texttt{0x00007fffffffe4a0},\\
\text{新值} &= \texttt{0x00007fffffffe400},\\
\text{差值} &= \texttt{0xa0}=160\ \text{字节}.
\end{aligned}
\]

`leave` 等价于 `movq %rbp, %rsp; popq %rbp`：它从 `0(%rbp)` 弹出这个被改过的值，于是函数返回后调用者的 `%rbp` 比正确值**低了 160 字节**。

**(3)** 调用者之后的代码全部用 `%rbp` 作为基准访问自己的局部变量、参数和保存的返回地址。帧指针一错位，这些访问就整体偏移了 160 字节：

\[
\begin{aligned}
\text{调用者以为的保存位置} &: \%rbp_{\text{旧}}+0,\ +8,\dots\\
\text{实际读到的位置} &: \%rbp_{\text{旧}}-160,\ -152,\dots
\end{aligned}
\]

也就是说，调用者的 `leave` 会从错误的位置弹出旧的 `%rbp` 和返回地址。若这 160 字节范围内有攻击者能写入的数据（例如被调用函数的缓冲区、或调用者更早读入的输入），攻击者就能让调用者从"自己的数据"里取返回地址，从而劫持控制流。这就是**帧指针偏移（frame shift）**攻击：不需要覆盖返回地址，只改一个字节的 `%rbp`，把整个调用者的栈帧"挪"到攻击者布置的数据上。

**为什么想到**：单字节只能改 `%rbp` 的低 8 位，但栈帧的局部变量和返回地址都是相对 `%rbp` 定位的，`%rbp` 一动，后续所有相对访问都跟着动——改一个字节就能移动最多 255 字节的"视野"。

**(4)** 开栈保护后，布局变成：

\[
\begin{aligned}
-16(\%rbp) &\sim -9(\%rbp) &&: \texttt{buf}\ (8\ \text{字节}),\\
-8(\%rbp)  &\sim -1(\%rbp) &&: \text{canary},\\
0(\%rbp)   &                 &&: \text{保存的旧 }\%rbp,\\
8(\%rbp)   &                 &&: \text{返回地址}.
\end{aligned}
\]

`i = 8` 写到 `-8(%rbp)`，即 canary 的最低字节。编译器生成 canary 时**最低字节被强制为 0x00**（这样字符串函数无法把它当普通字节写回），所以这次写入 `0x00` 等于**没有改变** canary 的值，函数返回前的比较照样通过，攻击者也就获得了「不触发保护地改变相邻内存一个字节」的能力（这里改的是 canary 自身，若缓冲区紧邻保存的 `%rbp`，改的就是帧指针）。

**为什么想到**：canary 检查比的是"整个 8 字节是否等于原值"；写入一个与原来相同的字节，差值仍为 0，检查当然发现不了。

**(5)** 三个角度：

- **代码**：把循环条件改成 `i < 8`（或用 `sizeof(buf)`、`memset(buf, 0, sizeof buf)`），从源头消除 off-by-one；对外部长度做「不小于 0 且不超过容量」的双向检查，注意无符号数下溢。
- **编译选项**：`-fstack-protector-strong` 能让更多函数插入 canary，`-D_FORTIFY_SOURCE=2` 让 `memset`/`memcpy` 在编译期或运行期检查对象大小；但注意本题的 NUL 单字节写**能绕过 canary**，所以不能只依赖 canary。
- **检查工具**：AddressSanitizer（`-fsanitize=address`）用红区（redzone）包住每个栈对象，能精确报出「越界 1 字节」；`-Warray-bounds`、静态分析器、fuzzing + ASan 也能在测试阶段发现。

## 常见错误

一是以为 `i=8` 写的是返回地址——返回地址在 `8(%rbp)`，`i=8` 只到 `%rbp`，改的是保存的旧 `%rbp`。二是把帧指针偏移量算成 8 或 255：这里是把 `0xa0` 清零，差值恰好 `0xa0=160`。三是认为开了 canary 就一定安全：canary 最低字节为 0，写入 0 的 off-by-one 恰好"隐身"，帧指针照样可能被改（取决于布局）。四是只改代码不跑工具：这种 bug 在小样本上可能"看起来正常"，必须用 ASan 或边界检查才能稳定发现。
