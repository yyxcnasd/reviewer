编译器把下面的求和循环展开 \(4\) 次，并用了两个累加器：

```c
long sum(long *a, long n) {
    long i = 0, s0 = 0, s1 = 0;
    for (; i + 3 < n; i += 4) {
        s0 += a[i] + a[i + 2];
        s1 += a[i + 1] + a[i + 3];
    }
    for (; i < n; i++)
        s0 += a[i];
    return s0 + s1;
}
```

回答：

(1) 当 \(n=10\) 时，第一个循环执行几次？第二个循环处理哪些下标？

(2) 为什么用两个累加器，而不是只用一个 `s`？

(3) 为什么循环条件是 `i + 3 < n`，而不是写成 `i < n - 3`？如果 `n` 的类型是 `size_t` 会怎样？

(4) 展开后整数结果与不展开时一定相同吗？如果数组元素是 `double` 呢？

## 提示

先看 \(n\) 除以 \(4\) 的商和余数：展开后的主循环每次处理 4 个元素，剩下的交给第二个循环。加法在 CPU 上是有延迟的，一条依赖链会串行等待；两条独立的链可以并行。无符号数的减法在 \(n<3\) 时会下溢。

## 解析

**(1)** 主循环条件 \(i+3<n\)：

- \(i=0\)：\(3<10\)，处理 \(a[0],a[1],a[2],a[3]\)，然后 \(i=4\)；
- \(i=4\)：\(7<10\)，处理 \(a[4],a[5],a[6],a[7]\)，然后 \(i=8\)；
- \(i=8\)：\(11<10\) 不成立，退出。

所以主循环执行 \(2\) 次，处理了前 \(8\) 个元素。第二个循环从 \(i=8\) 开始，处理

\[
a[8],\ a[9]
\]

两个元素，共 \(2\) 次。

**(2)** 单累加器 `s += a[i]` 中，每一次加法都要等上一次加法的结果，形成一条串行的依赖链。如果加法延迟是若干周期，CPU 即使有多个加法单元也只能排队。

用两个累加器后，`s0` 与 `s1` 是两条互不依赖的链，CPU 可以同时推进它们，把加法延迟隐藏起来。实际的循环里还会同时展开多条加载，效果类似。注意这只提高吞吐，不改变最终结果。

**(3)** 若把条件写成 `i < n - 3`，而 `n` 是 `size_t`（无符号数），当 \(n<3\) 时 `n-3` 会下溢成接近 \(2^{64}\) 的巨大值，条件变得极容易成立，循环继续访问数组，造成越界。写成 `i + 3 < n` 时，\(n<3\) 直接不进入主循环，余数循环会正确处理剩下的元素。

**(4)** 整数加法满足结合律，且在模 \(2^{64}\) 意义下结果唯一，所以展开、改变相加顺序都不影响最终整数结果。浮点加法不满足结合律：每一步都要舍入，\((a+b)+c\) 与 \(a+(b+c)\) 可能不同。所以对 `double` 数组，编译器通常不能随意做这种重排（除非开了不保证精度的快速数学选项）。

结论：**(1) 主循环 \(2\) 次，余下 \(a[8],a[9]\)；(2) 两个累加器形成两条独立依赖链，隐藏加法延迟；(3) 避免 `size_t` 下溢；(4) 整数结果相同，`double` 不一定相同。**

## 常见错误

一是忘记余数循环，导致 \(n\) 不是 \(4\) 的倍数时漏加元素。二是以为展开一定让程序快 \(4\) 倍：它只是给 CPU 更多并行机会，实际受加载带宽、加法吞吐等限制。三是把 `n - 3` 当成安全写法，忽略无符号下溢。四是认为「加法顺序随便换」，把整数和浮点混为一谈。五是展开时把 `s0 += a[i] + a[i+2]` 的配对写错，例如重复加同一个下标。
