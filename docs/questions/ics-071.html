64 位 x86-64 下，函数

long sh(long x, int n) { return x << n; }

编译成

sh:
    movq    %rdi, %rax
    movl    %esi, %ecx
    salq    %cl, %rax
    ret

(1) 求 sh(1, 64)、sh(1, 65)、sh(1, 63)、sh(1, -1) 的实际返回值，并解释 n = 64 为什么得到 1。

(2) 如果函数参数类型是 int（即做 32 位移位，指令为 sall %cl, %eax），那么 n = 31、n = 32、n = 64 分别得到什么？为什么掩码位数会变？

(3) C 标准对移位量 n 有什么要求？为什么 sh(1, 64) 在 C 里是未定义行为，而汇编却"有确定结果"？

(4) 编译器在 -O2 下可能怎样利用"未定义行为"？举一个"常量折叠结果与硬件结果不同"的例子（不必写出具体数值，说明为什么不可依赖即可）。

(5) 如果确实想利用 x86 硬件的"按位取模"语义写跨平台安全的代码，应该怎么写？

提示+
%cl 只有 8 位，x86 的移位指令会再按操作数宽度取模：64 位操作数用 n mod 64n\bmod 64nmod64，32 位操作数用 n mod 32n\bmod 32nmod32。C 标准与此无关：它规定移位量必须小于类型宽度且非负，越界就是未定义行为。

解析（先自己做一遍再看）展开
答案

sh(1,64)=1、sh(1,65)=2、sh(1,63) 与 sh(1,-1) 都等于 −263-2^{63}−263；硬件把移位量按操作数宽度取模（64 位取低 6 位、32 位取低 5 位）；C 标准规定越界移位是未定义行为，编译器可以假设 n 在 [0,64)[0,64)[0,64) 内做优化

(1) x86 的 64 位移位只使用 %cl 的低 6 位作为移位量，即实际移位 n mod 64n\bmod 64nmod64：

    sh(1, 64)：64 mod 64=064\bmod64=064mod64=0，左移 0 位，得 1； sh(1, 65)：65 mod 64=165\bmod64=165mod64=1，得 2； sh(1, 63)：左移 63 位，2632^{63}263 的位模式是 0x8000000000000000，作为有符号数是 −263-2^{63}−263； sh(1, -1)：%cl 是 0xFF，取低 6 位得 636363，所以同样是 2632^{63}263 的位模式，得 −263-2^{63}−263。

为什么想到：salq %cl, %rax 的移位量来自寄存器，硬件不会检查范围，只用 %cl 的低 log⁡264=6\log_2 64=6log2​64=6 位；movl %esi, %ecx 只是把 32 位参数放到 %ecx，真正起作用的是 %cl 的 8 位里的低 6 位。

(2) 32 位操作数只用 %cl 的低 5 位：

    n = 31：左移 31 位，0x80000000，作为 int 是 −231-2^{31}−231； n = 32：32 mod 32=032\bmod32=032mod32=0，得 1； n = 64：64 mod 32=064\bmod32=064mod32=0，得 1。

为什么掩码位数会变：移位是"在操作数的位宽内移动"，32 位寄存器只有 32 个位置，超过 31 的移位量硬件取模 32；64 位取模 64。所以同一段 C 源码，int 版和 long 版在 n = 32 处表现完全不同。

(3) C 标准规定：左移/右移的移位量必须非负且小于类型宽度，否则是未定义行为。sh(1, 64) 在 C 层面越界，编译器可以假设它不会发生；而汇编指令对移位量取模是硬件定义的行为，两者不是一回事——"汇编有确定结果"不能推出"C 程序有确定结果"。

(4) 编译器可以利用"n 一定在 [0,64)[0,64)[0,64) 内"这一假设做优化，例如：

  • 范围分析：如果 n 来自 [0,64) 之外的比较分支，编译器可以删掉某些检查；
  • 常量折叠：sh(1, 64) 这种常量表达式可以直接被算成任意值（不同编译器、不同版本可能给 0、1 或警告），因为它本来就属于未定义行为；
  • 代数化简：(x << n) >> n == x 之类的变换只在 n 合法时成立，编译器可能据此改写。

所以写 C 时不能依赖 x86 的"取模"行为；这类代码换编译器、换优化级别就可能出错。

(5) 若确实想要"按位取模"的语义，必须显式写出来：

long sh(long x, int n) {
    return (long)((unsigned long)x << (n & 63));
}

要点：先把 x 转成无符号（避免左移溢出/符号位问题），再把移位量与 63 相与，把语义固定成"模 64"；或者用 n % 64（注意 n 为负时 C 的 % 结果可能为负，要配合无符号）。更好的做法是先判断 n 在 [0,64) 内，否则按业务逻辑返回错误，而不是依赖硬件行为。

常见错误展开

一是以为 sh(1, 64) 会得到 0（"移光了"），忽略硬件取模。二是把 %cl 的 8 位当移位量，忘记还要按操作数宽度取模，导致 32 位与 64 位结果混为一谈。三是把"汇编结果确定"等同于"C 程序结果确定"，在 C 里依赖未定义行为。四是写跨平台代码时只加 n & 63 却忘了先把 x 转成无符号，左移溢出仍是问题。
