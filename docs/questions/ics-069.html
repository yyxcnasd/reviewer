数组与结构体 · 综合题

计算机系统概论 综合题 难度 自编 投稿：自编
导出这道题 ICS-069 · ←→ 翻题 · E 展开 · D 记已做

考虑下面的类型：

struct Header {
    char magic;
    int  version;
    short flags;
};

struct Payload {
    struct Header h;
    char   name[5];
    double weight;
    union { long id; char code[8]; } u;
};

(1) 求 sizeof(struct Header)、sizeof(struct Payload) 以及 Payload 各成员的偏移。逐处说明填充是为什么产生的。

(2) Payload 的填充字节一共有多少？name 结束（偏移 16）到 weight 开始（偏移 24）之间的那 7 个字节，内容是否确定？

(3) 下面的代码有什么问题？

struct Payload p;
struct { char buf[20]; int counter; } b;
strcpy(p.name, "abcd");
memcpy(b.buf, &p, 24);
printf("%d\n", b.counter);

问：拷贝了多少字节、buf 有多大、溢出几字节、counter 被源结构体的哪几个字节覆盖？打印结果能预测吗？

(4) 若把 weight 改成 float，重新求 sizeof(struct Payload) 与各成员偏移，说明对齐规则的变化。

(5) 如果把这个结构体直接 memcpy 到网络缓冲区发给另一台机器（对方按大端解析、并按同样的结构体读），会出现哪些问题？

提示+

对齐三规则：成员偏移是自身对齐的倍数；结构体总大小是最大对齐的倍数；不满足就插填充。union 的成员共享起始地址、大小取最大成员。memcpy 只有字节，没有类型，所以既不会被目标数组大小截断，也不会自动跳过填充。

解析（先自己做一遍再看）展开
答案

Header 大小 12（magic 0、version 4、flags 8，填充 3）；Payload 大小 40（h 0、name 12、weight 24、u 32，填充共 10 字节）；memcpy(b.buf, &p, 24) 把 24 字节写进 buf[20]，溢出 4 字节并覆盖 counter，源字节 20–23 位于未初始化的填充区，counter 的值不可预测

(1) 先看 Header：magic 占 1 字节（偏移 0），version 是 int、要 4 对齐，所以偏移 4（1–3 是填充），flags 是 short、2 对齐，偏移 8–9；结构体最大对齐是 4，总大小补到 12（10–11 是尾部填充）。

Payload：

h name weight double 要 8 对齐，17–23 填充 7 字节 u union 含 long，8 对齐；weight 结束于 31，32 已是 8 的倍数，无需额外填充
成员 偏移 说明
0 占 12 字节
12 5 字节，占 12–16
24
32

等一下，weight 已在 24–31，u 的 8 对齐地址从 32 开始，所以 u 在 32–39。最大对齐是 8，总大小 40，没有尾部填充。

因此

sizeof(struct Header)=12,sizeof(struct Payload)=40.\texttt{sizeof(struct Header)}=12,\qquad \texttt{sizeof(struct Payload)}=40.sizeof(struct Header)=12,sizeof(struct Payload)=40.

(2) 填充共 333（Header 内）+ 777（name 到 weight 之间）=10=10=10 字节。这些字节是编译器插入的、没有名字的空间：C 只保证它们存在，不保证内容。局部变量 p 没有初始化时，填充区里是栈上残留的旧数据，每次运行都可能不同。

(3) 逐项数清楚：

    memcpy 拷贝 24 字节；
  • 目标 b.buf 只有 20 字节；
  • 因此溢出 24−20=424-20=424−20=4 字节，写到 buf 之后紧邻的成员上；
  • 结构体 {char buf[20]; int counter;} 中 buf 占 0–19、counter 占 20–23（int 对齐 4，20 正好满足），所以溢出的 4 字节全部落进 counter；
  • 这 4 字节来自源结构体偏移 20–23，即 name 之后、weight 之前的填充区。由于 p 没有初始化，这 4 个字节是未定义的残留值。

所以 counter 被改写成一个不可预测的值，printf 的结果取决于栈上残留数据；程序可能"看起来正常"（残留恰好是 0），也可能输出任意数——这正是未定义行为类 bug 难查的原因。

为什么想到：memcpy 的第三个参数是字节数，与目标容量无关；要判断溢出多少，必须先算清目标对象的内部布局（buf 与 counter 的偏移），再把源结构体的字节区间一段段对齐过去。

(4) weight 改成 float（4 字节、4 对齐）：

    h 0–11，name 12–16； weight 4 对齐，17 之后的第一个 4 的倍数是 20，所以偏移 20–23（17–19 填充 3 字节）； u 要 8 对齐，24 已是 8 的倍数，所以偏移 24–31；
  • 最大对齐 8，总大小 32。

sizeof(struct Payload)=32,\texttt{sizeof(struct Payload)}=32,sizeof(struct Payload)=32,

填充变成 3+3=63+3=63+3=6 字节。注意"把 double 换成 float"不只是成员小 4 字节，后面整个成员的偏移都会变，memcpy 的字节数、网络协议的字段偏移也必须跟着改。

(5) 至少三类问题：

  • 字节序：x86-64 是小端，version 这类多字节整数直接 memcpy 出去是大端机器读不懂的，必须逐字段做 htonl 之类的转换；
  • 填充字节：10 个填充字节的内容不确定，直接发送会泄露栈上残留数据，对方按结构体解析时也会因为布局不同而错位；
  • 对齐与 ABI：不同编译器/平台可能给出不同的大小与偏移（例如 32 位与 64 位、MSVC 与 GCC 的对齐规则差异），接收端必须用显式的序列化格式（每个字段按固定宽度、固定字节序打包），不能依赖 sizeof(struct)。
常见错误展开

一是把 Payload 的大小按成员大小相加算成 12+5+8+8=3312+5+8+8=3312+5+8+8=33 或 36，忘记 weight 要 8 对齐、尾部要补齐。二是把 name 到 weight 之间的填充当成"可以放心 memcpy 的数据"，忽略它内容不确定。三是算溢出时只比较 24 与 20，却说不清覆盖了哪个成员——必须先算出 counter 的偏移。四是认为 memcpy 会"按目标大小截断"；它不会，超出的部分照写不误。
